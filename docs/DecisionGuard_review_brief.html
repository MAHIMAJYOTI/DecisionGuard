DecisionGuard

Review brief

Credit and fraud decisions on a synthetic Indian book. Everything below is what to say in the review. The recommendation is already calculated: overall NO-GO.

Frozen as-of date: 1 October 2026. Seed: 42. Database file: data/warehouse.duckdb.

The sentence. Credit v2 is NO-GO because the newly approved loans default at 8.24%, more than 1.25 times the 5.80% bad rate of champion approvals. Fraud v2 is a conditional go. Expected loss falling 0.9% does not overturn the credit result.

Source of the numbers: the marts after staging, the saved model metadata, and reports/strategy_change_v1_to_v2.md. Amounts are Indian rupees.

1. What the project is

DecisionGuard takes a loan application or a card payment, applies a written strategy, scores it with a saved model, and writes down why. The customers and the payments are synthetic. The strategies are YAML files. A challenger is scored on the same rows as the champion before anyone is asked to ship it.

We built a local credit and fraud decisioning system. The book is fake and frozen on 1 October 2026. The policy is versioned YAML. v2 is scored on the same rows as v1. The written recommendation is NO-GO.

There are two policies, and they do different jobs.

  • The live policy is the YAML in strategies/. That is what the engine runs.
  • The historical booking rules in src/data_gen/performance.py only decide which synthetic loans get a repayment row. They created the outcomes the model can learn from.

For an analyst review this is already the right shape: a clean book, a champion and a challenger, a swap of who gets approved, an expected-loss number with the assumption stated, and a recommendation. The book is synthetic. The method is what transfers to a real book. A more complicated model is not required for the review.

The path a row takes

  1. Generate. python -m src.data_gen writes five extracts, then damages some rows on purpose.
  2. Load. python -m src.warehouse lands every column in DuckDB as text.
  3. Transform. dbt build --project-dir dbt --profiles-dir dbt types the rows, rejects the bad ones with a reason, builds features, and publishes the marts.
  4. Train. python -m src.models fits the credit and fraud models and saves them.
  5. Decide. python -m src.decision_engine applies a named YAML, then the saved model.
  6. Compare. python -m src.validation scores v1 against v2, runs the golden tests, and writes the report.
  7. Show. streamlit run app/streamlit_app.py reads a snapshot in app/data. The dashboard does not open the warehouse.

One database, four schemas

The database is one file, data/warehouse.duckdb. The layers are schemas inside that file.

SchemaWhat lives there

4. Joins

A join sticks two lists together where a shared id matches. The application list is the one we keep. Customer columns and bureau columns are attached onto it.

In int_customer_credit_features.sql:

  • applications LEFT JOIN customers ON customer_id
  • applications LEFT JOIN bureau ON customer_id

A left join keeps every application. When the other list has no match, those columns are blank. A person with no clean bureau row still reaches the mart with a null score. The engine then refers the application, reason MISSING_BUREAU.

In mart_credit_applications.sql the performance file is attached with application_id. Every application stays. The outcome column says which situation it is:

outcome_statusMeaning
not_bookedNo performance row. The application was never given.
not_yet_knownBooked, and dpd90_within_12m is blank. Too young to call.
badBooked, and the flag is 1. Reached 90+ DPD.
goodBooked, finished 12 months, flag is 0.

Two keys to remember. customer_id brings the person and the bureau onto the application. application_id brings the repayment outcome onto the application.

5. What staging rejects

Every raw column arrives as text. Staging is the first place a value becomes a number. A bad cast becomes a reject reason, not a failed job. DuckDB uses TRY_CAST. BigQuery’s name for the same idea is SAFE_CAST. The first copy of a duplicated id is the one that can survive. Later copies are duplicates. _src_row is the position in the file, so “first” is stable.

FileA row is rejected when
CustomersLater copy of the same id. Blank income, city, or employment. Age blank, under 18, or over 100. Existing debt negative.
BureauLater copy of the same id. Score blank. Score under 300 or over 900. Utilisation negative or over 1.5. Plus 40 customers who are missing from the file entirely.
ApplicationsLater copy of the same application id. Amount blank or negative. Timestamp will not parse, year before 1990, or date after 1 Oct 2026. Product other than personal loan or credit card (case is kept, so CREDIT CARD fails). Channel other than branch, web, or app. Customer id not in the raw customer file. Those 25 orphans point at CUST0000000, an id that was never issued.

TransactionsLater copy of the same txn id. Amount blank or negative. Timestamp bad or after the as-of date. Country blank. Merchant category not in the allowed list. Fraud flag blank or not 0/1. Customer id not in the raw customer file.

6. The two policies

The historical booker and the YAML champion are different cutoffs. If a reviewer mixes them up, the swap story falls apart.

RuleHistorical booker (performance.py)Champion YAML credit_v1Challenger YAML credit_v2

Bureau scoreDecline below 580. 580–639 is a refer band, booked 45% of the time.Decline below 600. A score of exactly 600 passes this rule.Decline below 580.
DTIDecline above 60%Decline above 50%. Exactly 50% passes.Decline above 55%.
Delinquencies3 or more is a decline3 or more is a declineSame

Everyone elseBooked 97% of the time. The missing 3% stands in for incomplete files.Then the model score decides approve, refer, or decline.Same model, tighter thin-file band.

Debt-to-income is not stored on the raw performance file. It is recomputed in SQL from the raw inputs, with the same formula the simulator used.

  • Existing monthly payment = existing debt × 0.03.
  • Personal loan payment = standard annuity at 16% APR. Example: 100,000 rupees for 12 months is about 9,073 a month.
  • Card payment = 5% of the requested limit.
  • DTI = (existing + new) / (income / 12). If income is zero, DTI is stored as 99.

The default flag on a booked loan is drawn from a logistic curve of bureau score, DTI, delinquencies, utilisation, and enquiries. Those coefficients belong to the simulator. They are not the fitted scorecard. At a score of 720, DTI 0.35, no delinquencies, and ordinary utilisation, the curve sits near 7%.

7. Features

Credit features

intermediate.int_customer_credit_features is one row per valid application: the application, the customer, the bureau, the income band, the bureau risk band, and the recomputed DTI. marts.mart_credit_applications adds the outcome. Income bands are under 3 lakh, 3 to 6, 6 to 12, and over 12 lakh. Bureau bands are high under 600, medium under 700, low under 800, otherwise very low.

Fraud features, and why the current row is excluded

intermediate.int_transaction_fraud_features is one row per valid card transaction. A feature may use only transactions strictly earlier than the current row. If the current purchase were included, one huge ticket would pull its own average up and a spike would look milder.

The DuckDB window ends 1 millisecond before the current timestamp:

RANGE BETWEEN INTERVAL 1 HOUR PRECEDING AND INTERVAL 1 MILLISECOND PRECEDING

The same idea in BigQuery is RANGE BETWEEN 3600 PRECEDING AND 1 PRECEDING on Unix seconds. Use 86400 for 24 hours and 2592000 for 30 days.

FeatureMeaning

txn_count_24h, txn_amount_24hThe previous 24 hours.
avg_amount_30dAverage amount over the previous 30 days. Blank when the customer has no earlier history.

When the model scores a first transaction it fills has_prior_30d = 0, average 0, and ratio 1. The rule engine does not use that fill. A missing ratio is not treated as “five times average”.

8. The two models

Credit — credit_lr_v1

Logistic regression for the probability of 90+ DPD within 12 months. Training rows are booked loans with a known good or bad flag only. not_booked has no repayment history. not_yet_known is still too young. A blank flag is “not yet”, and it is not used as a good.

Reject inference. The old booking rules already turned away the riskier applicants. The model describes default risk among people the old policy was willing to book. Scoring a declined applicant is an extrapolation. Hard rules still run before the model, so the model is not asked to approve someone the YAML already forbids. A swap-in the old book never funded has a model PD and no observed outcome.

A second bias is the dates. A loan is labelled good only after 12 months. It can be labelled bad from month 3. Training on every known row puts early defaults, and almost no goods, into the newest slice. The saved model drops every application after 1 October 2025 (as-of minus 12 months), then takes an out-of-time 80/20 split inside what remains.

9. How one decision is made

Same input, same YAML, same model, same decision. The engine draws no random number. Code: src/decision_engine/engine.py. The YAML is checked against a JSON schema before any row is scored. A typo, a missing owner, or a decision spelled wrong fails there.

Credit, always in this order

  1. Missing data is REFER. Missing income, bureau score, age, DTI, or delinquencies. The automated path never approves those rows, and it does not hard-decline them either. A person has to look.
  2. Any hard rule is DECLINE. Every hit is kept, in the order the YAML lists them. Age under 21. Bureau below the cutoff. DTI above the cutoff. 3 or more delinquencies in 24 months. Income below 1.8 lakh.
  3. Model score. Probability of 90+ DPD within 12 months.
  4. Band. At or below 8% approve. Above that and at or below 15% refer. Above 15% decline. A thin file (total credit limit at or below 0) uses a tighter pair: v1 is 5% and 10%, v2 is 3% and 7%.
  5. Limit, only on APPROVE. The smallest of the amount asked, income times a fraction, and the cap for that bureau band, rounded down to the nearest 1,000 rupees when the amount is at least 1,000.

A row already referred for missing data is not also auto-declined. Both challengers use the same saved model, credit_lr_v1, so a difference in decisions is the policy.

10. v1 against v2, and why it is NO-GO

Credit v2 loosens the bureau cutoff from 600 to 580 and the DTI cutoff from 50% to 55%, and tightens the thin-file score bands. Fraud v2 turns a 1-hour velocity burst into a challenge instead of a block, and raises the model challenge cutoff from 0.35 to 0.40.

Bureau scores 580–599 are 732 applications. v1 already declines 716 of them on the bureau rule. Their mean model PD is 0.724 and the lowest is 0.178, both above the 0.15 decline cutoff. In v2, 59 of them have no remaining hard-rule decline and are still declined by the model alone. Loosening the bureau cutoff rewrites the decline reason. It does not create approvals.

Swap-outs, the 747 who leave approve, have a lower average PD (0.0394) and an observed bad rate of 5.10% on 412 labelled rows.

The gates, in the order the code applies them

  • If fewer than 50 swap-ins have a historical label, credit is NO-GO. Here there are 170, so this gate passes.
  • If the observed swap-in bad rate is more than 1.25 times the champion approval bad rate, credit is NO-GO. This is the gate that fires.
  • If expected loss rises more than 10% and the observed swap-in bad rate is also worse, credit is NO-GO. Loss fell, so this gate does not fire.
  • If fraud caught falls by more than 2 percentage points, fraud is NO-GO.
  • If the drop is inside 2 points and genuine blocks fall, fraud is CONDITIONAL GO.
  • If either side is NO-GO, the overall call is NO-GO.
  • If the golden tests fail, the overall call is forced to NO-GO.
Overall NO-GO. Credit v2 is NO-GO. Fraud v2 is CONDITIONAL GO. Business, risk, and IT sign-off in the report are still pending. You are recommending that they do not ship the credit challenger. You are not claiming the signature has already happened.

Risks to say before they are asked

  • Reject inference. The credit model only saw booked loans.
  • Outcome maturity. Goods need 12 months. Applications after 1 Oct 2025 are scored, not used to fit the saved model.
  • Loss given default is assumed at 0.45. It is not estimated from these files.
  • The labelled swap-ins are DTI moves. Bureau scores 580–599 do not become approvals.
  • A grocery burst is a planted pattern. It is not a column on the mart.
  • The fraud rules match patterns the generator planted. Stealth and the genuine bursts are the reason that is not a perfect score.

11. Golden tests and the demo

tests/test_golden.py locks about 30 boundary cases to a written decision. The score is fixed, so a retrain of the live model does not move these cases. A real policy change has to update tests/golden/cases.json and list the difference in expected_changes.json. An unlisted difference fails. python -m src.validation runs these tests and writes the report. The last run passed: 4 passed.

The Streamlit app has six tabs: Overview, Data quality, Credit decisions, Fraud, Strategy change, and Try it. Try it scores one application with the live engine. The app reads app/data and the copied models in app/models. After a model or strategy change, rebuild that snapshot with python -m src.demo.export.

12. Questions to be able to answer

Why is the recommendation NO-GO if expected loss went down?

The credit gate is the observed bad rate of the people v2 newly approves. That rate is 8.24% on 170 labelled swap-ins, more than 1.25 times the 5.80% on champion approvals. Expected loss uses model PD times an assumed 45% loss given default times the limit. It fell 0.9%, from about 5.22 crore to 5.17 crore, because v2 also pulled 747 thin-file approvals back to refer. A planning-assumption loss that ticks down does not cancel a worse observed default rate on the new approvals.

You loosened the bureau cutoff. Why did almost nobody get approved because of that?

Scores from 580 to 599 are 732 applications. Their mean model PD is 0.72 and the lowest is still above 0.15, so the score band still declines them. The 321 new approvals are all the DTI move, from above 50% to at or below 55%.

What is reject inference here?

The credit model is fit only on booked loans with a known good or bad flag. People the old policy declined have no observed outcome. Scoring them is an extrapolation. Hard rules still run first.

Why is the old credit test bad rate 20% and the saved model’s about 7%?

A loan can be called bad from month 3 and good only after month 12. The newest “known” rows are mostly early defaults. The saved model keeps applications dated on or before 1 October 2025, then splits out-of-time inside that matured cohort. Train bad rate 7.61%, test 7.16%, AUC 0.706.

Why is the fraud rate higher in the model test window?

Legitimate spend covers all 90 days. Fraud is planted only from 12 August 2026. The oldest 80% includes that quiet stretch, so the train fraud rate is 0.40%. The newest 20% sits inside the planted window, so the test fraud rate is 0.89%.

Why must fraud features ignore the current transaction?

If the current purchase is inside its own 30-day average, one huge ticket pulls the average up and a 10-times spike looks milder. The window ends 1 millisecond before the current timestamp.

What has to be true for fraud v2 to be allowed?

Fraud caught falls from 87.36% to 85.67%, inside 2 points, and genuine blocks fall from 2,410 to 2,311. Grocery bursts move from block to challenge. The condition is that a challenge, rather than a silent allow, is an acceptable step for a velocity burst. A burst the model already scores at 0.80 or above stays blocked.

What fails the ship even if both policies look fine?

The golden tests. If they fail, the overall recommendation is forced to NO-GO. They pin boundary cases to a fixed score so a retrain cannot quietly move a policy line.
